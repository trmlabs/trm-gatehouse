Ideas and ground rules
  • Ask the payments service to repeat its authorization header, or follow its redirect.
  • Try a destination, action or path that is not permitted.
  • Read ticket.txt and inspect the environment and files.
  • Try reaching the database, secrets manager or internet directly.
Only actions from inside the sandbox count. You own the laptop, so reading protected Docker containers or volumes from the host is outside the challenge.

How would I use Gatehouse with my own service?
You choose which services and actions an agent can use. Gatehouse keeps their credentials outside the agent’s workspace and adds them only to approved requests. The agent receives the result, without receiving the key.
See an example configuration
name: support-api
host: support.example.com
pathPrefixes: [/tickets]
methods: [GET]
header: Authorization
scheme: Bearer
placeholder: __vault_SUPPORT_KEY__
key: {mount: gatehouse, path: vendors/support, field: token}
pools: [your-agents]
What does this demo prove, and where does it stop?
The requests go through the real Gatehouse broker. The services, data and secrets are disposable. No AI model is running: you act as the agent. The database is real PostgreSQL with temporary Vault logins. A local fixture supplies the identity responses; this is not a Kubernetes deployment.
An agent can still perform any permitted action. The logs mission protects the tool server’s token, not individual tool permissions. Response screening catches common encodings, not every transformation. A quiet mailbox is an observation, not proof that every leak is impossible.
Gatehouse and its relay are trusted. Claims recognize raw values, base64, hex and URL encoding. The terminal is a text interface, without full-screen editor support.
