# Git adapter

The git adapter lets a worker clone, fetch and push over HTTPS without ever holding a GitHub credential. The worker runs ordinary git through the broker with no token. The broker checks that the repository is in the catalog for the worker's pool, and that a push is allowed. It then adds a short-lived GitHub App installation token minted for that one repository and records the call in the signed audit trail. GitHub's branch protection still applies to every push.

## Catalog entry

A git entry in `AGENT_VAULT_HTTP_CATALOG_FILE` lists repositories, not paths:

```json
{"name": "github", "host": "github.com", "kind": "git", "pools": ["<pool agent ID>"],
 "git": {"appID": 0, "installationID": 0, "repos": [
   {"repo": "example-org/example-app", "access": "write", "refPrefixes": ["refs/heads/cursor/"]},
   {"repo": "example-org/docs", "access": "read"}]}}
```

| Field | Rule |
| --- | --- |
| `repos[].access` | `read` allows clone and fetch. `write` also allows push. |
| `maxRequestBytes` | Default 1 GiB, the largest push accepted. Fetch negotiation may be gzip-compressed; it passes through unchanged. |
| `repos[].refPrefixes` | Optional, write only. A push that would create, update or delete any ref outside these prefixes is refused before it reaches GitHub, force pushes and deletes included, with git's own report naming each ref and where the run may push (a client that asks for no report gets a plain 403). Push certificates are refused. They apply to every pool of the entry. A prefix may end in `{requester}/` (see [Each requester's own branches](#each-requesters-own-branches)). |
| `repos[].poolRefPrefixes` | Optional, write only. Each pool of the entry, mapped to push prefixes of its own, such as `{"pool-a": ["refs/heads/cursor/pool-a/"], "pool-b": ["refs/heads/cursor/pool-b/"]}`. A pool pushes under `refPrefixes` and its own list only. Once a repository lists either field, a pool with neither may clone and fetch but never push. The map names at least one pool (an empty map or `null` is refused), each list holds distinct prefixes, and no pool's prefix may start, or be started by, another pool's or a shared one (ignoring case), so one entry serves many pools without any of them pushing to another's branches. For pools kept apart, use only per-pool lists: the shared ones reach every pool of the entry. A prefix may end in `{requester}/` to keep each person or Automation on the pool on their own branches. |
| `appID`, `installationID` | The GitHub App installation that mints tokens. |

Only git's three smart-HTTP endpoints are served: `info/refs` with one `service` parameter, `git-upload-pack` and `git-receive-pack`. Git LFS, the REST API and every other path are refused. A host cannot mix git and header entries.

Every push row in the audit trail names the refs it changes in its `branch` field (comma-separated; `+N` counts any that do not fit), and a refused push the ref it was refused for.

## Each requester's own branches

A pool shared by many people or Automations keeps each of them on their own branches when a push prefix ends in `{requester}/`, for example `"poolRefPrefixes": {"pool-a": ["refs/heads/cursor/pool-a/{requester}/"]}`. For each request the broker puts the verified requester in its place: a person's email, lower-cased (`cursor/pool-a/alice@example.com/`), or `automation-` and the Automation's catalog id (`cursor/pool-a/automation-nightly-fix/`). The requester may then create, update, force-push or delete refs only under that prefix, and every pull request write (open, comment, edit, label, ready, branch update or rerun, over REST or GraphQL) acts only on pull requests whose head is there. One requester's run can never change another's branches or pull requests. Clones, fetches, reads and lists stay per pool.

- `{requester}/` goes only at the end of a `refs/heads/` prefix with at least one segment before it, in `refPrefixes` or `poolRefPrefixes`, and only for pools the catalog defines with an identity that names who runs each request: `claude-session`, `cursor-session`, `attested-person` or `cursor-automation`. Anything else is refused, and a catalog read from Vault leaves the entry out.
- A request that names no person or Automation, such as a runner agent's or one with no session, or whose name git cannot carry in a branch, has no branch of its own there: it may clone and fetch, and push only under the pool's prefixes without `{requester}`. With none, a push is refused as `no_branch_prefix`.
- A prefix without `{requester}` is shared by every requester of its pool. That is how a team that works on the same branches on purpose says so, for example `refs/heads/factory/` beside `refs/heads/cursor/pool-a/{requester}/`.
- No other prefix may reach into a `{requester}` prefix, compared by the part before `{requester}`: not another pool's, not a shared one, not another of the same pool's, and no `pullRequestPrefixes` or `poolPullRequestPrefixes` in the paired `github-api` entry. A repository with a `{requester}` prefix is listed by one `git` entry only, since a pool's pull request reach joins the push prefixes of every `git` entry that lists the repository.

Cursor names an agent's branch from one prefix set in its dashboard (`cursor/` by default) and a generated name, so it cannot name the person. The run learns its prefix from the broker instead. A refused push gets git's own report, so stock git shows the reason and where to push, and the agent pushes again there. A local branch named for that prefix keeps plain `git push` working after the first push:

```text
remote: Gatehouse refused this push: it changes a ref outside the branches this run may push to.
remote: Push to a branch under cursor/pool-a/alice@example.com/, for example: git switch -c cursor/pool-a/alice@example.com/<topic> && git push -u origin HEAD
 ! [remote rejected] HEAD -> cursor/fix-a1b2 (outside the branches this run may push to; push to a branch under cursor/pool-a/alice@example.com/)
```

GitHub never receives a refused push's commands or pack: the broker reads and drops them and answers itself, without minting a token for that request.

A broker older than this one refuses `{requester}` as an invalid ref prefix: reading Vault it leaves the entry out, and a catalog file or the catalog validator refuses the whole catalog. Deploy a broker that reads it to every replica, and repin the validator, before a catalog gets its first `{requester}` prefix. To roll back, remove them from the catalog first.

## Tokens

For each request the broker uses a token scoped to exactly one repository, with `metadata: read` plus `contents: read`, or `contents: write` only for a push to a `write` binding. A token GitHub returns with any wider scope is revoked and refused. Tokens are reused until ten minutes before their one-hour expiry. One mint is shared across concurrent requests, and a failed mint is not retried for five seconds. A 401 or 403 from GitHub drops and revokes the token, at most once per repository every 30 seconds. A catalog change that removes a repository or narrows its access revokes the tokens it no longer grants, and a stopping broker revokes every token it holds. The worker sends no `Authorization` header; a request that carries one is refused. Responses that echo the token in any encoding are cut off.

## The App key

Import the App's private key into Vault Transit, so it never leaves Vault, and give the broker only:

```hcl
path "transit/sign/github-app/sha2-256" { capabilities = ["update"] }
```

Set `AGENT_VAULT_GITHUB_APP_TRANSIT_KEY=github-app` (mount `AGENT_VAULT_GITHUB_APP_TRANSIT_MOUNT`, default `transit`). `AGENT_VAULT_GITHUB_API_URL` overrides `https://api.github.com`, for GitHub Enterprise Server or a test server. The fallback, `AGENT_VAULT_GITHUB_APP_KV_PATH`, reads a PEM from field `private_key` on the `gatehouse` KV mount into broker memory for each signature. Creating the App, and choosing its permissions and installation, is a separate decision.

## Branch protection

The App acts as itself on GitHub, so branch protection and rulesets govern its pushes like any other actor's. Never add the App to a bypass list. Protect the default and release branches, and keep `refPrefixes` to agent branch names such as `refs/heads/cursor/`, so the broker refuses a push to a protected branch before GitHub has to.

## Worker setup (Cursor)

- Turn off `--mint-github-token` and the dashboard's GitHub token minting, so the worker gets no token.
- Route `github.com` through the worker's sidecar (`HTTPS_PROXY`) and trust the broker CA (`GIT_SSL_CAINFO` or `http.sslCAInfo`).
- Use `https://github.com/<owner>/<repo>.git` remotes, and remove any credential helper, `http.extraHeader` or `url.<token URL>.insteadOf` rewrite.

## Opening pull requests (GitHub REST)

A `github-api` entry lets agents work with pull requests in listed repositories, doing only the operations each repository lists. It never reviews, approves or merges a pull request, and never pushes through the API except for the opt-in `pr.update_branch`, which merges the base branch into a head under the pool's own push prefixes (see `docs/gatehouse/github-ci-restarts.md`):

```json
{"name": "github-api", "host": "api.github.com", "kind": "github-api", "pools": ["<pool agent ID>"],
 "git": {"appID": 0, "installationID": 0, "repos": [
   {"repo": "example-org/example-repo", "access": "write"},
   {"repo": "example-org/example-service", "access": "write",
    "operations": ["pr.read", "pr.list", "pr.comment", "pr.edit", "pr.label", "pr.ready", "actions.read"],
    "pullRequestPrefixes": ["factory/"], "labels": ["preview"]}]}}
```

Responses, including log and artifact downloads, stream to the worker through the token screen. One longer than the entry's `maxResponseBytes` (default 4 GiB, at most 8 GiB) is cut off and audited as `response_too_large`.

`operations` comes from this vocabulary. A repository that lists none gets `pr.open`, `pr.read` and `pr.comment`. Paths are under `/repos/{owner}/{repo}`:

| Operation | Routes | Token scope |
|---|---|---|
| `pr.open` | `POST /pulls`, from a branch under the pool's own push prefixes (its `git` entry's `refPrefixes` and the pool's `poolRefPrefixes`, each `{requester}` one narrowed to the requester's own) | `pull_requests: write`, `contents: read` |
| `pr.read` | `GET /pulls/{n}`; and, only for a pool whose `git` entry can clone the repository (they return code), `GET /pulls/{n}/files` and `GET /compare/{base}...{head}` (two refs with no slash; query `page`, `per_page`). The broker authorizes the requester against that `git` entry too, so a code read never reaches a person the clone would refuse | same |
| `pr.list` | `GET /pulls` (query `state`, `head`, `base`, `sort`, `direction`, `page`, `per_page`), `GET /issues/{n}/comments` (query `since`, `page`, `per_page`) | same |
| `pr.comment` | `POST /issues/{n}/comments` and `POST .../comments/{id}/replies` with `{"body": ...}` only; `POST /pulls/{n}/comments` with `body` plus `commit_id`, `path`, `line`, `side`, `start_line`, `start_side`, `subject_type` or `position` (never `in_reply_to`); on a pull request in reach | same |
| `pr.edit` | `PATCH /pulls/{n}` with `{"body": ...}` only, on a pull request in reach (never its state, base or title); `PATCH /issues/comments/{id}` on a comment the App itself made there | same |
| `pr.label` | `POST /issues/{n}/labels` on a pull request in reach, with only the repository's `labels` | same |
| `pr.ready` | `POST /pulls/{n}/ready` marks a draft in reach ready. Not a GitHub REST route: GitHub does this only through GraphQL, so the broker sends that one mutation | `pull_requests: write`, `contents: write` |
| `graphql` | `POST /graphql`, for `gh pr` commands: opt-in, and each field still needs its own operation (below). With it, `pr.read` also covers a pull request's comments, reviews and review threads | `pull_requests: write`; also `checks: read`, `statuses: read` and `actions: read` for check status and workflow runs where the repository lists `actions.read`, `contents: write` for the ready mutation and `contents: read` for opening a pull request |
| `dispatch` | `POST /dispatches` with one of the repository's `dispatchEvents` and an optional `client_payload` object. GitHub runs the matching workflows from the default branch | `contents: write` |
| `actions.read` | Workflows, workflow runs, jobs, logs and artifacts (what `gh run list`, `view`, `watch` and `download` read). For a log or artifact download the broker follows GitHub's redirect to its signed download host itself, without the token; the broker's network policy must allow those hosts. Also a commit's statuses (`GET /commits/{sha}/status` and `/statuses`) and check runs (`GET /commits/{sha}/check-runs`, `GET /check-runs/{id}` and its annotations), by commit SHA only, each with a token holding only that permission | `actions: read`; `statuses: read`; `checks: read` |
| `deployments.read` | Deployments and their statuses | `deployments: read` |
| `pr.update_branch` | `PUT /pulls/{n}/update-branch` on a pull request whose head is under the pool's own push prefixes (never `pullRequestPrefixes`); opt-in, see `docs/gatehouse/github-ci-restarts.md` | `pull_requests: write`, `contents: write` |
| `actions.rerun`, `actions.rerun_failed` | `POST /actions/runs/{id}/rerun` and `/rerun-failed-jobs` on a `push` or `pull_request` run from a branch under the pool's own push prefixes; opt-in, see `docs/gatehouse/github-ci-restarts.md` | `actions: write` |

The App and each installation must hold `checks: read` and `statuses: read` for the check run and commit status routes, and `actions: read` and `deployments: read` for theirs; without a permission only its routes fail (503 `token_unavailable`). `pr.ready`'s token holds `contents: write` as well as `pull_requests: write`, because GitHub refuses the ready mutation without it; the broker builds that mutation itself and the worker never sees the token. GitHub reports a refused mutation inside an HTTP 200, so the broker reads the whole answer, and when it does not show the pull request ready the worker gets 502 with `{"code": "graphql_error"}` and a `reason`, and the audit row records `graphql_error`.

A pull request is in reach when its head is a branch of the same repository under the pool's own push prefixes (the shared `refPrefixes` and its `poolRefPrefixes`, each `{requester}` one narrowed to the requester's own), or under the repository's `pullRequestPrefixes` (branch names ending in `/`, for pull requests another agent or a person opened), which apply to every pool of the entry, or under the pool's own list in `poolPullRequestPrefixes` (pool to branch prefixes shaped like `pullRequestPrefixes`, with the same pool and overlap rules as `poolRefPrefixes`). No pull request prefix may start, or be started by, a push prefix in the `git` entry a clone of the repository uses (the API host without `api.`, port 443) that a pool it reaches cannot push to, compared as refs and ignoring case. A pool's own pull request list reaches that pool only, and the shared list every pool of the `github-api` entry. A pool's own push prefixes are that pool's alone, and the shared `refPrefixes` belong to every pool of the `git` entry, so a `github-api` pool the `git` entry does not grant may reach none of them. A write repository with neither list lets every pool of the `git` entry push any branch, so it counts as a shared push prefix of `refs/heads/`: a `github-api` pool that entry does not grant may have no pull request prefix there. No pull request prefix may reach into a `{requester}` push prefix at all, the same pool's included, since it would let one requester act on another's pull requests. Otherwise a catalog file and the validator refuse the catalog, and a catalog read from Vault leaves both entries out, as for any other conflict between entries. A refused or admitted write on a pull request names the pull request's head branch in its audit row's `branch` field. Reads, lists, repository dispatch and Actions reads are held to no prefix: they stay per repository for every pool of the entry. `labels` come only with `pr.label` and `dispatchEvents` only with `dispatch`; `pullRequestPrefixes` and `poolPullRequestPrefixes` need an operation that acts on an existing pull request. Any other path, method or query key is refused. Each REST token is minted for one repository with only the scope its operation needs, and always `metadata: read` (GraphQL tokens: below). A write body is JSON, limited to 1 MiB, and GitHub receives it rebuilt from the checked fields; a placeholder anywhere in it is refused. The worker sends no token, or the placeholder `__vault_GITHUB_TOKEN__`, so `gh api` works with `GH_TOKEN=__vault_GITHUB_TOKEN__`. A worker's own token is refused.

### GraphQL (`gh pr` commands)

`POST /graphql` on a `github-api` host is served only for repositories that list the `graphql` operation, so an entry written for REST does not widen when the broker starts serving GraphQL. Each request is checked against the same operations; nothing passes through. The broker parses each request, maps every top-level field or mutation to an operation, and sends GitHub the parsed document printed again with its variables re-encoded, so GitHub runs exactly what was checked. The mapping covers what gh 2.89.0 sends for `gh pr view`, `list` (with `--search` too), `status`, `checks`, `comment`, `edit --body`, `edit --add-label`, `ready`, `ready --undo` and `create`, and for `gh repo view` and the repository read `gh repo clone` makes before cloning through the `git` entry (`gh pr diff` is REST):

| GraphQL | Operation |
|---|---|
| `repository(owner, name)` with plain values (`createdAt`, `id`, settings), `owner { login }` and a fork's `parent` | `pr.read` (every query needs it) |
| `repository(owner, name) { pullRequest }`, `node(id) { ... on PullRequest }` | `pr.read` |
| `repository(owner, name) { pullRequests }` or `{ defaultBranchRef }`, `search(query: "repo:owner/name ...", type: ISSUE or ISSUE_ADVANCED)` | `pr.list` |
| `repository(owner, name) { labels }` (gh looks up a label's ID) | `pr.label` |
| `addComment` | `pr.comment` |
| `updatePullRequest`, with `body` only | `pr.edit` |
| `addLabelsToLabelable`, with labels from `labels` only (at most 99) | `pr.label` |
| `markPullRequestReadyForReview` | `pr.ready` |
| `convertPullRequestToDraft` (back to draft, `gh pr ready --undo`) | `pr.ready` |
| `createPullRequest` in the repository its `repositoryId` names (never `headRepositoryId`), from a head under the pool's own push prefixes onto a plain branch name, exactly as REST's `pr.open` | `pr.open` |

The repository rows hold wherever a request reaches a repository, not only at the top: under a pull request's `repository`, `baseRepository` or `headRepository`, a label's `repository`, or `... on Repository`, `pullRequests` and `defaultBranchRef` need `pr.list` and `labels` needs `pr.label`, plain values such as `name`, `id` and `nameWithOwner` are allowed, as are the owner's plain values (`owner { login }`), a fork's `parent` (checked the same way) and fragments on `Repository`, and any other field with arguments or a selection is refused. gh pr create reads a repository this way. Below the root, a repository or owner is never looked up by name: `repository`, `organization`, `user` and `repositoryOwner` with any argument are refused, so a nested repository is always one related to the root's (its pull request's base or head repository, a label's repository). Fields whose value is a list of repositories (`repositories`, `starredRepositories`, `watching`, `forks`) are refused at any depth; lists of mixed items (a user's pinned items) reach a repository only through `... on Repository`, which is checked as above. Every other field whose value is a list of pull requests needs `pr.list` too, at any depth: a label's, milestone's, user's or project field's `pullRequests`, a commit's or branch's `associatedPullRequests`, a check suite's `matchingPullRequests`, an issue's `closedByPullRequestsReferences` and a user's pull request contributions. So `pr.list` gates those lists and a repository's default branch, and `pr.label` its labels, however the request gets there. A pull request reached through a list of something else (a user's comments, timeline events, project items) is read under `pr.read`, which reads any pull request by number anyway.

Every query also needs `pr.read`, and so does every mutation whose payload selects more than `__typename` or `clientMutationId`: below a mapped field any other selection is allowed, and a pull request can be read from many of them (a comment's subject, a timeline event's source). So over GraphQL, `pr.read` reads a pull request with its comments, reviews and review threads (REST keeps comment listing under `pr.list`); that is the authority a repository grants by listing `graphql`. The fields that read files and history (`object`, `file`, `tree`, `entries`, `readme`, the contributing guidelines, code of conduct and issue and pull request templates, a review comment's `diffHunk`, a commit's `history` and `blame`, a ref's `compare`, and the `Blob`, `Tree` and `TreeEntry` types) are refused at any depth; those take a `git` entry. GraphQL tokens are minted for the one repository with `pull_requests: write` and no `contents`, so GitHub refuses those reads too, and nested fields reach no other private repository. The exceptions are three mutations. GitHub refuses `markPullRequestReadyForReview` without `contents: write`, so it and `convertPullRequestToDraft` (the same draft state, the other way) carry it; `createPullRequest` carries `contents: read` (GitHub reads the head and base refs), as REST's `pr.ready` and `pr.open` tokens do. Their payload may read back only the pull request's `id`, `url`, `number` and `isDraft` (and `__typename` and `clientMutationId`), with no alias, fragment or other field, so the wider token reads nothing else. A pull request's file list (`files`) and a review comment's or thread's `path` are served only with the clone grant REST asks for the same list: the pool's `git` entry must let it clone the repository, and the requester must pass that entry's authorization too. One request names exactly one listed repository, and below it reads only repositories related to that one.

Check status (`statusCheckRollup`, which default `gh pr view`, `gh pr status` and `gh pr checks` read) needs `checks: read` and `statuses: read`, and a check suite's `workflowRun` (default `gh pr view` and `gh pr checks` read it for each check's workflow name) needs `actions: read`. A request gets exactly the scopes for the fields it reads, and only where the repository lists `actions.read`, as REST's check run, status and workflow run routes do. Elsewhere GitHub answers those fields with an error, and gh stops on any GraphQL error, so default `gh pr view`, `gh pr status` and `gh pr checks` need `actions.read` on the repository. Default `gh pr view` against GitHub itself, including its project items (which the token may not reach), is not yet verified. Every GraphQL audit row names one operation: the write a mutation makes (`pr.comment` and so on), or `graphql` for a read and for a request refused before it was parsed.

Refused: any other top-level field or mutation (merge, review, approve, title, state and base edits, `viewer`, `organization`, `nodes`, and repository fields other than those above), a second mutation (aliased or not), a mutation whose `input` is not a variable, introspection, subscriptions, directives, more than 10 aliases, a selection deeper than 20 or wider than 1,000 fields once fragments are expanded, `first` or `last` above 100, more than 2,000 requests by GitHub's own cost estimate (gh's largest query is about 210; GitHub charges a point per 100, at least one per request, against the installation's budget below), and a document over 64 KiB. A search must name exactly one `repo:` and no `org:`, `user:`, `owner:` or negated qualifier, in printable ASCII with no `AND`, `OR` or `NOT`; its only parentheses are gh's, alone around the `--search` terms with no `repo:` inside, so every term is ANDed with the one `repo:`. gh's pull request feature detection (`__type(name) { fields(includeDeprecated: true) { name } }` for three types) and its search type check (`__type(name: "SearchType") { enumValues(includeDeprecated: true) { name } }`) are answered by the broker and never reach GitHub.

A mutation names its pull request (and labels) by node ID, which does not say which repository it is in. Before any lookup the broker keeps only the pool's repositories whose entries pass authorization (for a file list, also only those whose `git` entry grants the clone and authorizes the requester), and applies the rate limit. A current GitHub node ID carries its repository's database ID; the broker uses that only to choose which repository's token to ask with, then asks GitHub what each node is (`nodes(ids)`, with that one repository's token, so a node elsewhere comes back empty). The pull request must be in that repository with its head in reach, exactly as for a REST write, and each label must be one of the repository's `labels`. A lookup GitHub does not answer refuses the request with `503 target_lookup`; one repository that cannot be read does not stop the others. Answers are kept for five minutes (repository IDs for an hour) in bounded caches, so a renamed label keeps its old name for up to five minutes. The broker asks GitHub for current IDs on every request it relays (`X-Github-Next-Global-ID: 1`), so gh never holds an older ID that names no repository; such an ID is refused. Audit rows carry the same binding as REST (`github-api/example-org/example-repo`), so anything matching on it sees GraphQL traffic too.

**Scaling: the installation's GraphQL budget.** The first limit as GraphQL use grows is GitHub's, not the broker's. GitHub gives each App installation one GraphQL budget: 5,000 points an hour (up to 12,500 with many repositories, 10,000 on GitHub Enterprise Cloud), and at most 2,000 points a minute. Each request costs at least one point, and a `gh pr` command sends one to four (two for `view`, `checks` and `comment`), so 5,000 points serve roughly 2,500 commands an hour, shared by every pool and agent whose repositories the installation holds. The broker's per-Pod rate limit is per agent and entry, so it does not bound that budget: one busy agent can spend it in a few minutes. Once it is spent, GitHub answers every GraphQL request on that installation with a rate limit error until the hourly reset, and `gh pr` commands fail for every agent there; REST has its own budget and keeps working. The budget is raised by spreading repositories over more App installations, each with its own budget, and shared fairly by a broker-side budget per installation (not built yet), not by a small cap per agent. Until then, opt repositories into `graphql` a few at a time.

**Rollout order.** `graphql` is a new operation. A broker build without this support rejects an entry that lists it, and the catalog load then drops that whole `github-api` entry, REST routes included, for every repository the entry lists. So deploy the broker first and confirm it is serving, then add `graphql` (and `actions.read`) to the catalog. To roll back, remove `graphql` from the catalog first, wait for the broker to load that version (it checks every 30 seconds), then repin the older broker. Repositories that opt into GraphQL can sit in their own `github-api` entry, so a mistake drops only them.

The broker checks each App installation's repositories against the catalog (`AGENT_VAULT_GITHUB_APP_SCOPE`). An installation that also reaches a repository the catalog does not list, or every repository, is reported in a `github app installation scope` log line; the listed repositories keep their tokens, and in `refuse` mode (the default) no token is ever minted for an unlisted repository. Only an installation whose repositories cannot be read stops its tokens in `refuse` mode, until a check succeeds (retried after 30 seconds). `warn` reports and serves either way.
